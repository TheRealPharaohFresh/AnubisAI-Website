A local-first command center

AI-assisted work, with decisions in your hands.

Anubis AI is a desktop assistant under development. Its current foundation combines a local command center, an approval-led coordinator, and a narrowly scoped software-development specialist.

Product capabilities below reflect the project's documented and tested development status. This site is not a public software release.

The command center

One place to see what’s happening.

The React and TypeScript interface connects to a local FastAPI service and SQLite database. The desktop shell is built with Tauri.

01

Tasks & progress

View queued and active work, task status, progress, results, and verification state. Task records persist locally across restarts.

02

Approvals & audit

Review work before execution and inspect recent tool decisions and outcomes. Audit entries are designed to avoid displaying file contents or command output.

03

Control & settings

Configure the workspace and model provider, cancel supported work, schedule one-shot local development runs, and pause new requests. Schedules retain normal approval gates; recurring schedules are not supported. Global pause does not stop a subprocess already running.

The agents that exist today

Two registered roles. Clear boundaries.

Agent names in future roadmaps are not implemented agents. The backend currently registers Anubis and Thoth.

Implemented

Anubis · Coordinator

Classifies requests, builds a bounded plan for supported software-development work, pauses for owner review, delegates approved work, and checks recorded evidence before reporting its outcome. Ambiguous and high-impact requests fail closed or require approval.

Implemented

Thoth · Software development

Works only in an owner-approved project workspace. Its bounded toolset can inspect, edit, and run approved development checks; paths are confined to the project and sensitive operations require additional approval.

Planned

Other specialists

Research, communications, voice, and other named agents are roadmap ideas, not registered implementations. Their names do not imply current capabilities or access.

How a development run works

Plan. Review. Execute. Verify.

For supported project work, the workflow is deliberately staged. Approval authorizes a specific next step; it does not itself mean the step was executed or succeeded.

Request & plan

Anubis classifies the request and prepares a bounded plan for an existing, configured project.

Owner review

Separate approvals gate the run and plan. Thoth then operates within the project boundary; sensitive files, deletions, or commands outside the allowlist require an additional approval.

Evidence & report

Supported tests and build checks can run through the restricted tool path. Anubis bases its report on recorded execution and test evidence.

Model choice

Local by default. Cloud only by choice.

Text generation can use a locally running Ollama model or optional Gemini and Groq cloud providers. ANUBIS does not automatically switch providers after an error.

Ollama · Local

Connects to a loopback Ollama service and lists models installed there. A live generation through the app’s provider layer was tested with qwen3.5:4b on an Intel Mac. Local generation can be slow and depends on the user’s hardware and selected model.

Gemini & Groq · Optional

Provider adapters, model discovery, and streaming are implemented, but no credentials are configured and live cloud use has not been tested. Cloud requests are off by default; enabling them sends prompts to the selected provider under its terms.

Usage controls

Cloud calls require explicit opt-in and configured model-price estimates and spending limits. Unknown prices and zero/default budgets block paid calls. Provider limits, availability, and charges depend on the user’s provider account.

The provider chat path does not receive tool definitions or action authority. Model responses alone do not run tools or execute tasks.

Local-first, not network-ready

Built for a local machine. Not for remote exposure.

The packaged app runs its backend on loopback and keeps its SQLite database in the app’s data directory. Gemini and Groq credentials are stored in the macOS Keychain, not SQLite. Local backups and restore utilities are available.

  • The API is intended to remain bound to loopback.
  • Authentication is not implemented. Do not expose the API to a network.
  • Global pause does not terminate a currently running subprocess; cancellation is separate.
  • Subprocess OS-level CPU and memory quotas and comprehensive secret discovery remain unfinished.
Security status
Permission checks, project confinement, approval gates, audit history, and provider budgets have implementation and test coverage described in the project checklist. Production security hardening and a full security review remain outstanding. Do not treat local deployment as a security certification.

Not part of the current product

What is still future work.

Clear boundaries matter as much as the feature list.

Voice & meeting assistance

No voice interface or audio-state API is implemented. Interview Assist is deferred and is not a current feature.

Autonomous broad task execution

The worker supports bounded Anubis/Thoth jobs and one-shot local development schedules. Arbitrary task categories and recurring schedules are not supported.

Alternate editions

Only the Anubis edition is configured. Zeus AI, Odin AI, and Anu AI are proposed future editions with no builds or installers. Edition selection is planned for the website, not the desktop app.

Availability

A development build exists. A public release does not.

The project checklist reports an unsigned, unnotarized Intel macOS app and disk image. Apple Silicon and other operating systems are not verified.
