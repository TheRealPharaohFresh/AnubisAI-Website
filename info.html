Product & technical information

A clearer picture of what’s built.

Anubis AI is an in-development, local-first desktop assistant. Here is the current architecture, provider status, and release readiness—without treating roadmap items as shipped features.

Current build

A desktop application has been built and tested.

The project checklist reports a local packaged application and verified workflows. That does not make it a supported or publicly available release.

Built locally

Intel macOS

An unsigned `.app` and `.dmg` with the FastAPI backend bundled. The packaged backend health endpoint and disk-image integrity were checked.

Not release-ready

Signing & notarization

The build is unsigned and unnotarized. macOS may require the owner to approve opening it. No official installer is offered here.

Unverified

Other systems

Apple Silicon and Windows/Linux builds have not been verified. There is no approved public system-requirements matrix.

The documented test machine is an Intel x86_64 Mac with 8 CPU cores and 16 GiB RAM. This describes the development environment, not minimum or recommended system requirements.

Architecture

Desktop shell, local API, local data.

The application combines established components rather than relying on a hosted Anubis service.

Desktop & interface

Tauri v2 desktop shell with a React, TypeScript, and Vite command-center frontend. The interface includes overview, tasks, approvals, audit history, and settings.

Backend & storage

FastAPI runs on loopback and manages workflows, permissions, and a SQLite database. In a packaged app, the database is stored in the app data folder.

Provider credentials

On macOS, Gemini and Groq keys use the system Keychain and are not stored in SQLite. If secure credential storage is unavailable, saving a key fails rather than falling back to plaintext.

Text generation

Choose a provider. No automatic fallback.

Provider connections are separate from action permissions: chat generation does not itself call tools or execute tasks.

Live-tested locally

Ollama

Connects only to a local loopback Ollama API. The project checklist reports a successful generation using `qwen3.5:4b`; that test took about 34 seconds on an Intel Mac with 16 GiB memory. Performance varies by model and hardware.

Implemented, not live-tested

Google Gemini

Provider adapter, model discovery, and text streaming are implemented. No API credential is configured, so live authentication and requests have not been verified.

Implemented, not live-tested

Groq

Provider adapter, model discovery, and text streaming are implemented. No API credential is configured, so live authentication and requests have not been verified.

Cloud privacy and cost: cloud use is disabled by default and requires an explicit setting. If enabled, prompts go to the selected provider under that provider's current terms. Rates are configured by the owner; unknown model prices or requests over configured budgets are blocked. Review each provider's terms before sending sensitive information.

Safety boundaries

Approval is part of the workflow.

The development workflow is intentionally bounded: work happens in an owner-approved project directory, backend permissions are checked when a tool is invoked, and sensitive actions can stop for approval.

  • Workspace paths are confined to the selected project; unsafe paths and command options are rejected.
  • Commands run from an allowlist without a shell; secrets are stripped from the process environment.
  • Credential access, deletes, and commands outside the allowlist require an approval request and are not run automatically.
  • Global pause defers new work and agent steps; it does not stop a subprocess already running.
  • Cancellation can terminate an active project subprocess through the backend.
  • API access is loopback-only; authentication is not implemented, so remote exposure is unsupported.

Development validation

Test evidence, not a production claim.

The supplied project checklist records successful local test and build runs, including isolated end-to-end software-development workflows.

Automated checks

The checklist reports 96 backend tests passing, along with frontend tests, lint, TypeScript checks, production build, Rust formatting, Clippy, and Cargo tests.

Still outstanding

Full security review, OS-level subprocess resource quotas, broader credential discovery/redaction, authentication for anything beyond local use, code signing, notarization, and verified builds for other targets.

Availability

Development build ≠ public release.

No installer is currently approved for public download. Review the release page for the exact status.
